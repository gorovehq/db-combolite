Theory of Operation Guidebook

A deep architectural analysis of the internal mechanics, memory model, crash invariants, multi-process coordination, and storage subsystems of the db-combolite engine.

1. Architectural Design & Philosophy

db-combolite is an embeddable, serverless, multi-model database engine engineered in pure C99. It bridges the operational footprint of SQLite with the polymorphic modeling power of modern distributed multi-model engines (Relational, JSON Documents, Embeddings/Vectors, Graph Links, Bit-Packed Time Series, and Content-Addressed Blobs).

Core Design Tenet: Zero Core Heap Allocation
All runtime scratchpads, working buffers, slot structures, and page caches are supplied directly by the caller or through the explicit cdb_env memory hooks. The core library never invokes malloc, realloc, or free directly, making it strictly determinable for microcontrollers, safety-critical systems, and constrained RTOS environments.

Key Guiding Invariants

  • Serverless & Self-Coordinating: There is never a daemon, server daemon, background broker, or listener port. Multiple OS processes accessing the same database coordinate purely via physical disk files (the archive and ephemeral companion delta tracks) using deterministic lock-free state machines.
  • Single File at Rest: When idle or closed, a database is exactly one durable file on disk (.cdbarch or .cdb). Companion files exist only while sessions are actively unsealed.
  • Strict Append-Only Merges & Copy-on-Write (CoW): The committed historical state of the archive is never overwritten in place. Logical pages are relocated on write; anchor maps point logical IDs to physical page offsets, ensuring crash-safe atomic swaps.
  • Clean-Room Architecture: All structures—B+Tree pager, vector neighbour graphs, bitwise time-series compressors, and CMBQL bytecode VM—are clean-room specifications optimized for embedded predictability.

2. Low-Level Storage Engine

Storage in db-combolite is abstracted behind cdb_storage, an abstract vector table representing block devices, memory-mapped flash, or host OS files.

2.1 File Header & Epochs (Spec 1.9, 14.1)

The archive file begins with a 512-byte dual header slot system (Slot A at offset 0, Slot B at offset 512). On host disks with 512-byte sectors, updating a slot is an atomic single-sector operation.

2.2 Copy-on-Write (CoW) Logical Pager

The pager exposes logical pages (numbered 1 .. $N$) that never change their logical identity. When page contents are mutated:

  1. The pager allocates a fresh physical page at the file's append point (or from the reusable free list).
  2. The modified payload is written to this new physical location.
  3. The Anchor Map is updated in memory so that the logical page ID maps to the new physical page number.
  4. Old physical pages are placed into a pending free list and become reusable only after a succeeding commit sequence fences out all read snapshots that referenced the old page.

2.3 Physical Anchor Map & Mirrored Roots

The Anchor Map is a specialized B+Tree that translates logical_page_id → physical_offset. To guarantee that a crash while updating the anchor map cannot destroy database navigation, the header maintains two roots: anchor_root and anchor_mirror_root. Writes are flushed and synchronized to the alternate root before the primary header commits.

2.4 Nibblets: Sub-Page Small Record Allocator (Spec 16, 14.18)

Storing small records (such as small JSON delta revisions, table row revisions, or sparse time-series blocks) in dedicated 4KB pages causes catastrophic internal fragmentation. db-combolite solves this via Nibblets:

  • Shared Slotted Pages: Dedicated pages (Type 0x0009) pack multiple small records (≤ 1/4 page size) across arbitrary stores.
  • Packed 64-bit Address: A nibblet address encodes (physical_page << 16) | slot_index with the high bit set, seamlessly distinguished from standard logical page IDs.
  • Two-Way Back References: Every nibblet record contains a reverse pointer [store_id, kind, index_key], enabling the engine to move or compact records without store coordination.
  • Reconciliation Merging: During reconciliation, pages under 50% utilization are merged together, updating the owner's index via cdb_doc_nib_moved or cdb_ts_nib_moved.

2.5 Overflow Page Chains (Spec 14.15)

When a document body, relational text column, or large BLOB exceeds the payload room of a single page (or nibblet limit), it overflows into a linked chain of Overflow Pages (Type 0x0007). The owning page records the total_byte_length and first_overflow_page_id. Overflow pages link linearly through a 64-bit next_page pointer in their header.

2.6 Ordered B+Tree Index Engine (Spec 14.8)

All secondary indexes, catalog bodies, document head indexes, and link stores utilize a zero-heap B+Tree with order-preserving binary keys. Keys are sorted lexicographically via unsigned byte comparison (memcmp), supporting prefix queries, exact point lookups, and bidirectional cursor scanning.

3. Concurrency, Multi-Process Coordination & Crash Safety

db-combolite achieves ACID transactions and multi-process concurrency without requiring background server daemons or OS-level advisory file locks.

3.1 In-Process Coordinator & Leader Election (Spec 5.2)

Each application process opening the database initializes an in-process Coordinator (cdb_coord). Coordinators claim slots in the coordination companion file:

  • Append → Settle → Choose: When multiple processes open the database concurrently, each appends a reservation ticket with its unique session ID and monotonic start time. After a settling interval, the process with the lowest session ID / start time assumes the Primary Coordinator role.
  • Heartbeat Monitoring: The primary maintains a periodic monotonic heartbeat in its slot. Subordinates monitor this timestamp. If the primary crashes or stalls beyond the heartbeat timeout, subordinates automatically execute an election to promote a new primary.
  • Background Heartbeat Thread (M20): On multi-threaded systems with thread hooks supplied, an autonomous worker thread keeps idle databases alive and renews heartbeats without stalling application loops.

3.2 The Baton Protocol & Reconciliation Fencing (Spec 5.3)

While all processes may append transaction deltas to their own private delta tracks simultaneously, only one process at a time may merge and fold deltas into the master archive. This exclusive right is called the Baton:

  • CTS Fencing: The baton is guarded by a monotonically increasing Commit Token Sequence (CTS). Every write pass during reconciliation checks the current CTS. If a process experiences a long OS suspension and attempts to write with an expired CTS, the write is immediately rejected by the pager.
  • Fair Handoff: The primary coordinator distributes the baton using round-robin queuing with early congestion detection (RED) under write-heavy loads.

3.3 Delta Tracks & Durability Levels

Writes are initially journaled to companion delta tracks (Write-Ahead Logs) allocated per coordinator slot (e.g. rel.0.wal).

Durability Level Commit Guarantee Recovery Behavior
CDB_DURABILITY_FULL Durable flush (fsync barrier) on both the delta record and commit record before returning. Zero acknowledged data loss after abrupt power cut.
CDB_DURABILITY_NORMAL (Default) Written to OS buffer cache; periodic sync barriers during checkpoint intervals. May lose transactions acknowledged in the last checkpoint window, but file is guaranteed uncorrupted.
CDB_DURABILITY_OFF Pure in-memory buffering without sync barriers. Designed for scratch/temporary datasets. Fastest throughput; vulnerable to power loss.

3.4 Crash Recovery & Reconciliation Protocol

When opening an archive after an abrupt termination, the coordinator executes a 4-phase recovery:

  1. Torn Write Truncation: Scans each companion delta track. Every record carries an independent CRC32C or AEAD auth tag. The track is truncated at the first record failing verification.
  2. Transaction Filtering: Only transactions containing an intact COMMIT record are preserved. Incomplete or aborted transactions are discarded.
  3. Baton Replay: Committed deltas are replayed in global commit order, dispatching mutations through the store apply hooks (cdb_doc_apply, cdb_vec_apply, etc.).
  4. Snapshot Promotion: Updated pages are synced to disk, the anchor map is updated, and the committed header slot is toggled atomically.

4. Native Multi-Model Engines

Rather than wrapping external formats, db-combolite implements tailored, highly optimized native structures for each paradigm within a single unified archive.

4.1 Relational Tables (Row & Column-Oriented)

Tables exist in two storage layouts sharing a common catalog schema:

  • Row-Oriented Tables (cdb_table): Stored as specialized document pools where each row is an encoded binary object keyed by column IDs. Columns support strict types, NOT NULL constraints, default values, primary keys, and secondary B+Tree indexes.
    Schema Evolution Without Table Rewrites
    Adding, dropping, or widening a column (e.g. INT32 → DECIMAL) writes a new schema version record to the catalog. Historical rows are read through the current schema definition on-the-fly: dropped columns are masked, new columns yield default values, and types are converted dynamically in memory.
  • Column-Oriented Tables (cdb_rowgroup): Ingested rows are batched into columnar row groups. Column chunks are compressed using LZMA2/xz (via third-party/xz) or bit-packing, offering high-ratio analytical compression (OLAP) on embedded devices.

4.2 Document Pools & BM25 Full-Text Search

A Document Pool stores schemaless or semi-structured JSON-like hierarchical values:

  • Revision Chains: Documents maintain a linear history: CDB_REV_ORIGINAL → CDB_REV_DELTA (patches) → CDB_REV_CHECKPOINT. Revisions are never discarded unless configured with a retention cap.
  • Built-In BM25 FTS Engine (cdb_fts): Configured document fields are tokenized into a term dictionary, inverted postings B+Tree (term, doc_id) → tf, and document length index. Searches compute exact BM25 probabilistic relevance rankings.

4.3 Vector Collections & Approximate Nearest Neighbor Graph

Vector collections manage dense embeddings for semantic search and agent memory:

  • Supported Types: F32, F16, BF16, I8, and 1-bit BINARY vectors across up to 65,535 dimensions.
  • Distance Metrics: Euclidean ($L_2$), Cosine Similarity, Inner Product (Dot), and Hamming Distance.
  • Neighbour Graph (HNSW-Class ANN): When enabled via cdb_vec_create_graph, collections maintain a graph of $K$ nearest neighbours. Search starts from Spread Points (≈ $\sqrt{N}$) and Reach Points, performing a best-first priority queue walk with direct traversal of pending mutations.
  • Source Tracking: Vectors track their source document version; query hits indicate if the underlying document has changed (staleness indicator).

4.4 Time Series Engine & Bit Codecs

Optimized for IoT telemetry and sensor streams, series are keyed by metric names and sorted tag sets:

  • Bit Codecs (cdb_tsbits): Timestamps are compressed using Gorilla-style delta-of-delta encoding. Float values are compressed using XOR bitwise difference packing. Categorical values use run-length dictionary compression.
  • Late Arrival Handling: Configurable policies per store: REJECT, ACCEPT (overwrite/merge), or HOLD (diverted to a held index and folded in during reconciliation).

4.5 Graph Links & Learned Neuron Weights

Links connect entities across any store (document → vector, table row → document, etc.):

  • Dual Mirrored Indexes: Maintained in forward (source, type, target) and reverse (target, type, source) indexes in the $links store.
  • Cardinality Enforcement: Validates 1:1, 1:N, and N:M constraints on commit.
  • Cascade Rules: CDB_LINK_ON_DELETE_TOMBSTONE, CASCADE, or REFUSE.
  • Neuron Weights: Links carry 32-bit floating point weights that can be reinforced or decayed dynamically, providing a substrate for learned associative memory graphs.

4.6 Content-Addressed Streaming Blobs

Arbitrary large binary objects are streamed chunk-by-chunk through cdb_blob_writer, bypassing memory limits by streaming directly into overflow page chains. Each blob is content-addressed by its cryptographic SHA-256 (or HMAC-SHA-256) digest, providing automated deduplication within encryption boundaries.

5. Structured Query Engine & Virtual Machine (CMBQL)

Queries and mutations are executed through a unified two-tier architecture: declarative/pipeline CMBQL compiling into a binary operator tree (CMBQ), and stored procedures compiling into register-based virtual machine bytecode (CMBP).

5.1 The 15 CMBQL Operator Nodes

Execution is Volcano-style: operators implement streaming cursors that pull tuples on demand under bounded memory:

5.2 Stored Procedure Virtual Machine (CMBP Bytecode)

Stored procedures run in a sandboxed, zero-heap virtual machine (cdb_proc_vm) featuring 64 registers ($R_0 \dots R_{63}$), 4 streaming query cursors, 8 nested savepoint frames, and instruction execution budgets to prevent infinite loops. The VM includes built-in dispatch for mathematical routines, signal processing (FFT, FIR filters), GIS geodesic distances (Haversine, Cross-track), and mutation operations.

6. CRDTs & Multi-Master Peer Replication

For decentralized, offline-first, and mesh deployments, db-combolite implements conflict-free replication primitives without requiring central locks:

  • Hybrid Logical Clocks (HLC): Combines physical wall-clock nanoseconds with a logical sub-tick counter and node ID (cdb_hlc) to provide strict total ordering of all distributed mutations.
  • Peer Version Vectors: Compact vectors track the synchronization high-water mark of up to 32 participating peers.
  • Conflict Resolution Rules:
    • Documents & Tables: Field-level Last-Write-Wins (LWW) based on HLC timestamps.
    • Graph Links: Add-Wins Observed-Remove Sets (AWORSet) ensuring concurrent additions dominate deletions.
    • Telemetry: Commutative idempotent point appends.
  • Transport-Agnostic Slices: The engine exports compact binary replication delta slices (cdb_db_crdt_export_slice) that can be transported over BLE, MQTT, HTTP, or sneakernet.

7. Security, Cryptography & Tamper Governance

Enterprise security and multi-tenancy are built into the physical disk format:

  • Envelope Encryption: Authenticated Encryption with Associated Data (AEAD) via AES-256-GCM or ChaCha20-Poly1305. Master keys unlock the file; per-enclave subkeys protect individual tenant stores. Plaintext is never exposed in swap or temporary files.
  • Deterministic Nonce Construction: Nonces are synthesized from (track_id << 64) | sequence_number, where sequence numbers are reserved durably to guarantee that a nonce is never reused across crashes.
  • Role-Based Access Control (RBAC): Principal identities are granted bitmask permissions (READ, WRITE, EXEC, ADMIN) scoped to specific stores or enclaves.
  • Tamper-Evident SHA-256 Hash Chaining: Critical governance events (key rotations, schema mutations, crash recoveries, and transaction revisions) are recorded to the reserved public audit series (CDB_AUDIT_STORE_ID). Each event incorporates the SHA-256 hash of its predecessor, creating a cryptographic audit trail that immediately detects retro-active modifications.

8. The CRUD Mutation & Deletion Engine Lifecycle

Every CRUD operation (Create, Read, Update, Delete) in db-combolite is governed by rigorous storage invariants that maintain crash safety, zero core heap allocation, and copy-on-write integrity.

8.1 Create Lifecycle & Sub-Page Allocation

When an entity is created (cdb_table_insert, cdb_doc_insert, cdb_vec_insert, cdb_link_add):

  1. Constraint & Schema Pre-Flight: The engine checks NOT NULL and UNIQUE constraints against both committed B+Tree secondary indexes and uncommitted modifications staged in the open transaction (via cdb_doc_get_in_tx and cdb_table_live_in_tx). Any violation aborts the call with CDB_E_SCHEMA or CDB_E_EXISTS before writing to disk.
  2. Entry ID Generation: The owning store allocates a strictly increasing 64-bit Entry ID from the catalog counter (persisted in the store's catalog record).
  3. Transaction Journaling: The mutation is appended to the current process's private delta track (e.g. rel.0.wal) alongside its CRC32C or AEAD auth tag.
  4. Reconciliation Placement:
    • Small Records (≤ 1/4 Page): Packed into shared slotted Nibblet Pages (Type 0x0009). A tagged 64-bit address (page << 16) | slot is recorded in the store's B+Tree index.
    • Medium Records (> 1/4 Page): Allocated dedicated CoW logical pages.
    • Large Records (> Page Size): Anchored in a revision head page with excess content chained into Overflow Pages (Type 0x0007).

8.2 Read Lifecycle, Snapshot Isolation & Zero-Copy Views

Readers in db-combolite require no read locks and never block concurrent writers:

  • Snapshot Visibility: Readers traverse B+Tree indexes using the physical page pointers committed in the latest active header slot. They are completely isolated from uncommitted deltas written by other processes.
  • Transaction-Local Reads: Inside an active write transaction, reading an entry checks the caller's staging cache (doc_stage) first. If the cache overflowed, it scans backwards through the transaction's own journal delta records to present a consistent read-your-own-writes view.
  • Zero-Copy Semantics: Readers decode byte slices directly into caller-owned page buffers. Dynamic string and binary fields point directly into the caller's buffer rather than copying memory to the heap.

8.3 Update Lifecycle, Delta Patches & Index Upkeep

Updating records differs by model to balance write amplification against history preservation:

  • Document Pools: Supports full replacement (cdb_doc_replace) and fine-grained delta patching (cdb_doc_patch). A patch stores an array of operations: [CDB_PATCH_SET / CDB_PATCH_REMOVE, field_path, new_value]. A new revision ID is issued (CDB_REV_DELTA), preserving previous revisions for auditability. Periodic full checkpoints (CDB_REV_CHECKPOINT) bound replay time.
  • Relational Tables: Supports delta column updates (cdb_table_update) and full replacements (cdb_table_replace). Only modified columns are processed; unchanged secondary indexes remain untouched, minimizing B+Tree churn. If keep_revisions = 0, older revisions are freed immediately.
  • Vector Collections: Embeddings are updated in-place inside their vector block slot. The entry is automatically registered in the neighbour graph's pending index for asynchronous priority queue re-linking.
  • Time Series Collisions: Ingesting a point with an existing timestamp overwrites differing fields in place, triggers the user's collision callback, and writes an audit event to the tamper-evident series.

8.4 Deletion, Tombstones & Space Reclaim

Deleting an entry enforces referential integrity before freeing physical media:

  • Referential Checks: Before deleting a document or table row, the engine calls cdb_link_check_delete. If a live link with CDB_LINK_ON_DELETE_REFUSE points to the entry, the deletion is rejected with CDB_E_STATE.
  • Tombstone Emission:
    • Documents: Appends a CDB_REV_TOMBSTONE revision to the chain. Links in both directions are tombstoned with flags indicating which entity was removed.
    • Tables: If retention is active, a tombstone revision is stored; if history is disabled, the head entry is erased from the primary index.
    • Vectors: The slot in the vector block is marked empty, the source index mapping is dropped, and the reverse neighbour graph unlinks the vector.
  • Nibblet Compaction & Page Freeing: Superseded nibblets leave dead slots. At reconciliation, pages with under 50% utilization are merged by cdb_doc_flush_pools, informing owners of new 64-bit addresses. Vacated pages are added to the reusable list once fenced by a subsequent commit.

9. Embedded Mathematical & DSP Engine Architecture

The db-combolite core includes a zero-heap, high-performance mathematical, digital signal processing (DSP), geodesic navigation, and linear algebra computing engine (cdb_math.h, cdb_math.c). Comprising 110 built-in scalar and vectorized functions, it allows mathematical evaluations to execute directly within the storage engine process boundary, eliminating the overhead of deserializing database records to external Python or R runtimes.

9.1 Zero-Allocation Memory & Numerical Stability Principles

Adhering to the engine's strict embedded memory philosophy, every function in the math engine is completely zero-heap. Operations requiring scratch memory (such as the Radix-2 Fast Fourier Transform, FIR convolution filters, and matrix multiplication) mandate caller-provided stack or static buffers.

  • Catastrophic Cancellation Protection: Functions like cdb_math_expm1(x) and cdb_math_log1p(x) use specialized Chebyshev and Taylor expansions to evaluate \(e^x - 1\) and \(\ln(1 + x)\) without loss of significance when \(|x| \ll 1\).
  • Euclidean Scaled Norms: cdb_math_hypot(x, y) and cdb_math_hypot3(x, y, z) compute distances by dynamically factoring out \(\max(|x|, |y|, |z|)\), preventing intermediate arithmetic overflow even when coordinate values approach \(10^{154}\).
  • Canonical Floating-Point Invariants: Quiet NaNs, negative zeros, and subnormal floats are sanitized according to Spec 14.6.5 to guarantee bitwise reproducibility across Little-Endian and Big-Endian architectures.

9.2 Geodesics, Spatial Indexing & GIS Projections

The geodesic subsystem operates on the WGS84 Earth reference ellipsoid model (spherical mean radius \(R = 6,371,000\) meters):

  • Haversine & Great-Circle Mechanics: cdb_math_haversine computes spherical distances using the numerically stable haversine formulation, while cdb_math_bearing calculates forward compass azimuths [0, 360) degrees.
  • Cross-Track & Along-Track Vectoring: cdb_math_cross_track_distance determines the perpendicular deviation in meters from a reference great-circle route, enabling real-time navigation cross-track error alerts.
  • Morton 2D Z-Order Bit Interleaving: cdb_math_morton2d normalizes latitude and longitude into 32-bit unsigned integers, then interleaves their bits into a single 64-bit integer. This maps 2D spatial coordinates onto a 1D space-filling Z-order curve, allowing standard B+Tree secondary indexes to perform bounded 2D spatial window queries with standard one-dimensional index scans.
  • Web Mercator & Tile Geometry: cdb_math_wgs84_to_mercator_x/y and cdb_math_lon/lat_to_tile_x/y project spherical geodetic coordinates to planar EPSG:3857 coordinates and OpenStreetMap slippy map tile raster grids.

9.3 Digital Signal Processing (DSP) & SDR Baseband Demodulation

Designed for Software-Defined Radio (SDR) and IoT time-series sensor streams, the DSP subsystem handles complex I/Q baseband data:

  • Instantaneous Polar Discriminator: cdb_math_iq_demod_fm demodulates frequency-modulated signals from successive I/Q sample pairs using a differential polar discriminator \( ext{atan2}(I_{t-1} Q_t - Q_{t-1} I_t, I_{t-1} I_t + Q_{t-1} Q_t)\), returning instantaneous frequency deviation in radians per sample.
  • Windowing Functions: cdb_math_window_hann, cdb_math_window_hamming, and cdb_math_window_blackman generate pre-computed spectral window tap arrays into caller buffers, reducing spectral leakage in subsequent FFT operations.
  • In-Place Radix-2 Cooley-Tukey FFT: cdb_math_fft executes complex discrete Fourier transforms in \(O(N \log N)\) time using in-place bit-reversal permutations, while cdb_math_fft_magnitude and cdb_math_fft_power compute single-sided spectral density across \(N/2 + 1\) bins.

9.4 Linear Algebra, ML Activations & Scientific Domains

The engine provides a complete suite of linear algebra and applied physics kernels:

  • BLAS-Class Vector & Matrix Operations: Dot product (cdb_math_vec_dot), Euclidean norm, cosine similarity, vector scaling, matrix multiplication (cdb_math_mat_mul), transposition, trace, and Gaussian elimination determinant calculation (cdb_math_mat_det).
  • Transformer & Neural Activations: In-engine activation functions including Sigmoid, ReLU, Error Function (erf), and GELU (Gaussian Error Linear Unit: \(0.5x(1 + anh(\sqrt{2/\pi}(x + 0.044715x^3)))\)).
  • Physical Science Kernels:
    • Astronomy: Topocentric pointing angles (Az/Alt/Range), equatorial RA/Dec conversions with sidereal time correction, Bennett optical refraction, and angular separation.
    • Electronics: NTC thermistor Steinhart-Hart and Beta models, ADC voltage conversions, RC low-pass cutoffs, LC resonance, and dBm/Watts power conversions.
    • Atmospheric & Fluids: ICAO barometric pressure-to-altitude hypsometry, Magnus dew point, humid air density, Pitot tube airspeed, Reynolds number, and Venturi flow rates.

9.5 Query Engine & Bytecode VM Integration

Math functions are seamlessly integrated across both query execution layers:

  • CMBQL Query Expressions: The SQL compiler matches function names during lexing and emits a CDB_QUERY_EXPR_CALL AST node bound to a 16-bit function ID (CDB_FN_*). Volcano operator trees evaluate expressions row-by-row with zero heap overhead.
  • CMBP Bytecode Virtual Machine: The 64-register stored procedure VM features a dedicated opcode CDB_BC_CALL_MATH (opcode 0x0B). The opcode fetches arguments from up to 8 input registers, calls the C99 math kernel, and deposits the result into a destination register in a single instruction cycle.
